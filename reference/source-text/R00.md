Flashcard App – Requirement 00
Mneme Domain Foundation – Learning Profile MVP Projection
Aligned with Project Mneme Foundation v2.3 and Project Mneme MVP Contract v1.2

| Role of this requirement: Translate the long-term Mneme Foundation into the stable domain contract used by the current offline-first Flashcard App. It intentionally implements only the MVP projection while preserving the Foundation boundaries needed for future general memory learning. |

## 1. Normative Dependencies
This requirement is the Learning Profile / Flashcard MVP projection of Project Mneme Foundation v2.3 and MVP Contract v1.2. It does not define Agent Memory semantics. Shared-core concepts (identity, provenance, scope, canonical history, projection, retrieval, replay, persistence) must remain compatible with Requirement 05 without forcing learner-specific entities into the shared core.

| Document | Role | Authority |
|---|---|---|
| Project Mneme Foundation v2.3 | Long-term research and architecture boundaries | Highest conceptual authority |
| Project Mneme MVP Contract v1.2 | Deliberately smaller implementation surface | MVP implementation authority |
| Requirement 00 – this document | Flashcard App domain projection and shared terminology | Normative for Requirements 01–04 |


## 2. Scope and Non-Goals
The current product remains a simple, reliable flashcard application. The domain underneath it must not assume that all future knowledge is vocabulary, single-fact, or single-turn question/answer content.
- Offline-first operation with no required AI or cloud dependency.
- Preserve the existing front/back review experience while replacing the domain foundation underneath it.
- Represent authored knowledge separately from learner history and model-derived state.
- Preserve stable identity, versioning, provenance, import reconciliation, and portable backup.
- Capture review history richly enough that future evaluators and memory models can reinterpret it.

### 2.1 Explicit non-goals for the MVP
- No Understanding Engine, tutoring engine, or total competence model.
- No requirement to implement KnowledgeStructure or KnowledgeProcedure renderers yet.
- No learned/AI EvidenceMapper in the core review path.
- No global knowledge ontology or automatic cross-unit canonicalization.
- No QTI/xAPI/Caliper dependency inside the internal model.
- No assumption that one mastery percentage is a universal truth about learner knowledge.

## 4. Knowledge Model – MVP Projection

### 4.1 KnowledgeUnit
KnowledgeUnit is the authored coherence, presentation/review, and provenance boundary. It is not assumed to be an atomic unit in human memory.
knowledge_unit:
  id: "ku_..."
  key: "english.word.accommodate"
  version: 4
  title: "accommodate"
  status: active
  component_ids: ["kp_meaning", "kp_spelling"]
  collection_ids: ["col_english_vocab"]
  provenance: {...}
- A vocabulary word, formula topic, historical topic, scientific concept, or work procedure may be represented as a KnowledgeUnit.
- Unit identity must remain stable across ordinary content edits; material identity changes require a new ID.
- KnowledgeUnit may reference components that are unit-local in the MVP while preserving future cross-unit reuse semantics.

### 4.2 KnowledgeComponent and KnowledgePoint
KnowledgeComponent is the general Foundation abstraction for assessable/revisable knowledge semantics. The MVP MUST implement KnowledgePoint. KnowledgeStructure and KnowledgeProcedure remain reserved extension points.
knowledge_point:
  id: "kp_..."
  key: "spelling"
  version: 1
  importance: 0.30
  provenance: {...}
- KnowledgePoint describes an authored modeling target, not a literal brain atom.
- Importance belongs to Knowledge; learner difficulty/retention belongs to learner/model state.
- Missing learner evidence for a point is unknown, not weak or forgotten.

### 4.3 Reserved component kinds

| Kind | MVP status | Meaning |
|---|---|---|
| KnowledgePoint | MUST IMPLEMENT | Discrete concept/property/meaning/condition/rule-like target. |
| KnowledgeStructure | SCHEMA RESERVATION | Learnable sequence, hierarchy, spatial/relational structure, distinct from knowledge-model metadata relations. |
| KnowledgeProcedure | SCHEMA RESERVATION | Durable procedural knowledge with steps/conditions/branches; not a general competence score. |


### 4.4 ComponentRelation
Typed relations among components are a Foundation capability but are not required for the MVP. Collection hierarchy must not be used as a substitute for semantic component relations. Specific relation vocabulary remains provisional.

### 4.5 Collection
Collection is organization/navigation metadata, not knowledge identity or learner mastery.
- Collection has stable ID/version, optional key, name, optional parent_id, order, and provenance where relevant.
- KnowledgeUnit-to-Collection membership is many-to-many.
- Dynamic learner views such as Due Today or Weak are filters, not Knowledge Collections.
- Retiring a Collection never implicitly deletes a KnowledgeUnit or learner history.

### 4.6 Asset and LearningSupport
- Assets use stable identity/version/checksum and local relative package references where practical.
- LearningSupport may include explanation, mnemonic, example, image, and hint definitions.
- Knowledge defines available support; learner history records actual support exposure/usage.
- Large binaries are not duplicated into each learner event when a stable versioned/checksummed reference is sufficient.

## 5. RecallForm
RecallForm is the authored semantic definition of a memory probe/activity. The name remains provisional at the Foundation level, but it is the normative implementation term for this MVP.
recall_form:
  id: "rf_..."
  version: 3
  type: self_assessed_flashcard
  stimulus: {...}
  interactions: [...]
  evaluation_spec: {...}
  tests: ["kp_meaning"]
  exposes: ["kp_meaning", "kp_spelling"]
  support: [...]
- Renderer implementation is not Knowledge ontology; Flutter chooses concrete UI.
- Declared test coverage means potential evidence, not evidence automatically obtained on every attempt.
- Active retrieval and exposure-only must be distinguishable.
- Related RecallForms should be eligible for contamination/sibling suppression when prior answer exposure would invalidate a later measurement.

## 6. LearningEpisode and LearningEvent
A bounded learning/review interaction is a LearningEpisode containing deterministically ordered LearningEvents. A simple flashcard review is the smallest useful projection of this model.
learning_episode:
  id: "ep_..."
  knowledge_unit_id: "ku_..."
  recall_form_id: "rf_..."
  recall_form_version: 3
  context: {...}

  events:
    - sequence: 1
      type: attempt
    - sequence: 2
      type: exposure
    - sequence: 3
      type: completion
- Event ordering inside an Episode is deterministic and independent of wall-clock timestamp.
- occurred_at and recorded_at are distinct concepts for offline-first operation.
- No global total order across devices/episodes is required by this MVP.
- Attempt, Hint, Exposure, Completion/Abandon are the initial vocabulary, not an exhaustive eternal taxonomy.

## 7. Observation, Evaluation, and Evidence
RawObservation
    ↓
Evaluator
    ↓
EvaluationOutcome
    ↓
EvidenceMapper
    ↓
MemoryEvidence

### 7.1 RawObservation
- Record what the learner actually did or submitted before inferring what it means.
- Preserve typed/structured raw responses when practical and privacy-appropriate.
- Exposure, hint requests, skip/abandon, and timing are observations; none automatically equal memory failure or success.
- Persist the richest useful observation subject to explicit privacy, retention, and data-minimization choices.

### 7.2 EvaluationOutcome
EvaluationOutcome records what the evaluator concluded about the response, such as exact-match result, normalized text result, selected option result, or self-rating interpretation. Evaluator identity/version and relevant normalization rules must remain attributable.

### 7.3 MemoryEvidence
- MemoryEvidence is an interpretation relevant to learner-memory inference; it is not the raw fact itself.
- Again / Hard / Good / Easy is an MVP self-assessment signal, not a universal evidence ontology.
- Absent/insufficient/ambiguous evidence remains absent/insufficient/ambiguous.
- Later reinterpretation may append new evidence derived from historical observations; it must not rewrite the historical observation.
- Evidence attribution rules/models carry provenance/version. A future learned mapper need not live in the Knowledge layer.

## 8. Learner Memory Model Boundary
Durable learning history
        ↓
MemoryModel / State Reducer
        ↓
model-specific LearnerState
        ↓
predictions / review need
        ↓
SchedulingPolicy
- LearnerState is latent/model-specific and rebuildable; it is not Knowledge and not durable historical truth.
- The MVP may persist point/unit state caches for performance, but they must be rebuildable for the supported model.
- Unknown is semantically distinct from weak/forgotten.
- A model may expose uncertainty when meaningful; deterministic models must not invent fake confidence.
- Future model-specific states such as FSRS-like stability/difficulty or BKT-like probability are adapters/payloads, not universal Mneme fields.

## 9. Scheduling and Selection Boundary
- Memory inference/prediction and scheduling policy are conceptually separate even if implemented in one module initially.
- FixedIntervalStrategy remains supported for backward compatibility.
- A local adaptive strategy may be added without changing Knowledge identity or learner history semantics.
- Scheduler decides when/what deserves review; RecallForm selection decides how to obtain useful evidence.
- No AI dependency is permitted on the normal scheduling critical path.
- new / learning / review / relearning may be used as MVP lifecycle labels only; they are not Foundation ontology.

## 10. Identity, Versioning, Provenance, and Lifecycle
- Core entity IDs are opaque, stable, immutable identities generated by the Knowledge Producer or migration adapter.
- Human-readable keys are optional and mutable; they are not identity.
- Same ID + same version MUST imply the same semantic content. Same version + different canonical content is a conflict.
- Ordinary content corrections/edits retain ID and increment version when semantic identity remains the same.
- Split/merge creates new IDs with optional lineage; learner state is not automatically copied or averaged.
- Retired is distinct from deleted. Historical entities referenced by learner history remain interpretable.
- Knowledge artifacts must be able to carry provenance such as source, producer, generation method, creation/update time, and lineage.

## 11. Knowledge Package Boundary
package/
├── manifest.yaml
├── memories/            # serializer name retained for MVP compatibility
│   └── <knowledge-unit-id>.md
└── assets/
- The package is a versioned interchange protocol, not the runtime database.
- Manifest owns package semantics; unit files own entity semantics. Do not maintain two authoritative copies of the same field.
- Collection membership is explicit metadata and must not be inferred from directory paths.
- Unit-local component serialization is acceptable in the MVP even though the Foundation permits future cross-unit component reuse.
- Knowledge Package, Learning Record Export, and Full Backup are separate protocols.

## 12. Import and Reconciliation
Package
  ↓ validate
  ↓ parse / normalize
  ↓ match by stable ID
  ↓ build ChangeSet
  ↓ transactional apply
  ↓ commit / rollback

| Condition | MVP rule |
|---|---|
| Local ID absent | Added |
| Same ID; incoming version higher | Updated after validation |
| Same ID; same version; same hash | Unchanged |
| Same ID; same version; different content | Conflict; never silently overwrite |
| Incoming version lower | Ignore/reject as stale |
| Absent from non-authoritative package | No meaning |
| Absent inside explicit authoritative scope | Membership removal / retirement candidate; never blind hard delete |

Knowledge reconciliation must never erase learner episodes, observations, evidence history, or historical interpretability.

## 13. Durability and Backup
The irrecoverable asset is learner observation history. Knowledge can often be recreated; historical learner interaction cannot.
Full Backup (conceptual)
├── knowledge/
├── history/            # LearningEpisode / LearningEvent / RawObservation
├── evaluations/        # historical outcomes where persisted
├── interpretations/    # historical evidence where persisted
├── config/
└── derived/            # learner/model/schedule caches; rebuildable
- Portable backup must restore Knowledge plus durable learner history sufficient to reconstruct the MVP experience.
- Derived learner/model/schedule caches are lower-authority and may be rebuilt.
- Backup format version, knowledge schema version, and event/evidence schema versions are separate concerns.
- Unsupported restore must fail before partial writes.

## 14. Legacy Flashcard Mapping
Existing Card / Collection
        ↓ migration adapter
KnowledgeUnit
  ├─ KnowledgePoint
  └─ self-assessed RecallForm

Existing reliable review/schedule history
        ↓
LearningEpisode / historical events
        ↓
derived learner state
- Preserve existing Collection names and memberships.
- Generate stable IDs once during migration and persist them thereafter.
- Do not reset learner history because content was normalized into the new model.
- Where legacy data lacks an observation dimension, preserve unknown rather than inventing values.
- Keep the existing front/back UI usable throughout migration.

## 15. Schema and Compatibility Principles
- Domain schemas are durable contracts; database schemas are implementation details.
- Old persisted data is decoded through version-specific readers into the current normalized domain model.
- Additive fields missing from old data remain absent/unknown rather than receiving misleading defaults.
- Semantic breaking changes require new fields/types/IDs rather than silently changing old field meaning.
- Current app writes current schema versions while reading the supported historical window.
- Migration fixtures must exist for legacy card data and each supported event/package schema version.

## 17. Acceptance Criteria
- An existing front/back card can be represented as KnowledgeUnit + KnowledgePoint + RecallForm without changing current UX.
- Knowledge import/update never resets or overwrites learner history.
- Re-import of identical stable knowledge is idempotent.
- One completed flashcard review produces a valid LearningEpisode with deterministic event order.
- Answer reveal/exposure is distinguishable from successful retrieval evidence.
- RawObservation, EvaluationOutcome, and MemoryEvidence are semantically distinct even if stored together physically.
- Missing legacy/history fields remain unknown rather than fabricated.
- Current learner/schedule state for the supported MVP model can be rebuilt from durable history.
- Fixed scheduling remains usable while a local adaptive strategy can be substituted behind the policy boundary.
- Portable backup can restore Knowledge plus durable learner history on a fresh installation.
- No deferred Foundation capability is required for normal offline use.

## 20. Implementation-Informed Domain Amendments (v2.2)
The following requirements incorporate patterns independently observed in Pi 1.0, claude-mem, DeepSeek Harness/Cordis, and Hermes without adopting their agent-memory ontologies.

### 20.1 Canonical history and one projection semantics
The historical store remains canonical. Any current learner-state, diagnostic, summary, scheduling state, or research projection is derived. All consumers must share one history normalization/projection contract so event compatibility and exposure semantics cannot drift between subsystems.

### 20.2 Durable operation identity
A completed learner interaction commit must carry a durable operation/submission identity suitable for retry-safe idempotency. Repeating the same operation identity must not create a second historical interaction.

### 20.3 Information origin and exposure provenance
Knowledge shown by the system before an attempt is part of historical context. The model must preserve enough provenance to distinguish independent retrieval from performance after hints, answer reveal, sibling exposure, worked examples, or other system-provided information.

### 20.4 Retrieval and projection boundaries
Exact identity and structured domain relations remain authoritative. Lexical/semantic retrieval may discover relevant artifacts but cannot define identity or learner truth. Rich knowledge/history may be exposed progressively and through purpose-specific budgeted projections.

### 20.5 Consolidation boundary
Knowledge artifacts can be candidates for deduplication/reconciliation under stable identity rules. Learner historical observations are evidence-bearing events and must never be collapsed because their content is similar.

## 21. Dual-Profile Boundary (v2.3)
Requirement 00 remains authoritative for the Learning Profile only. The following names are learner-specific unless separately promoted by Foundation v2.3: KnowledgeUnit, KnowledgeComponent, RecallForm, LearningEpisode, EvaluationOutcome, MemoryEvidence, LearnerMemoryModel, and SchedulingPolicy.
- Implementation namespaces SHOULD make this explicit (`learning.*` or equivalently named types). Existing public names may be retained as compatibility aliases during migration.
- Shared MemoryScope may be used by the Learning Profile, but its learning scope facets are profile-owned and must not define agent scope vocabulary.
- Learning history cannot be semantically deduplicated. Agent Memory may consolidate derived MemoryRecords under its own policy; that does not change this rule.
- Any shared persistence/retrieval primitive must preserve the richer provenance needed by both profiles rather than degrading one to fit the other.
