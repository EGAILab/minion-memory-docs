Flashcard App – Requirement 04
Local Domain Model & Persistence Contract v1.3
Aligned with Project Mneme Foundation v2.3, MVP Contract v1.2, Requirements 00–03, and shared-core compatibility with Requirement 05

| Core implementation rule: Persist durable semantics, not accidental implementation structure. The local database may be normalized for performance, but the domain contract must remain reconstructable, version-aware, and compatible with future Mneme model evolution. |
|---|


## 1. Purpose
This requirement defines the local persistence boundary for the first Mneme-aligned Flashcard/Learning Profile implementation. Foundation v2.3 now also has an Agent Memory Profile. This document remains authoritative for learning-profile persistence while reserving shared-core primitives (identity, provenance, scope, replay boundaries, projections, indexes, backup compatibility) that Requirement 05 can reuse without sharing learner-specific tables or semantics.
- Provide a durable local representation of Knowledge, learner history, and application configuration.
- Keep learner observation history protected from Knowledge import/update operations.
- Allow derived learner state and schedules to be rebuilt when models change.
- Support stable identity/versioning, provenance, package reconciliation, retirement, and lineage.
- Preserve the current Flashcard UX while replacing the old Card-centric persistence assumptions.
- Keep the storage contract compatible with later KnowledgeStructure, KnowledgeProcedure, richer events, and replaceable MemoryModels.

## 4. Logical domain records
The persistence implementation must be capable of representing the following logical records. These are domain records, not a mandate that every item becomes one SQL table.
- KnowledgePackageRecord — imported package identity, package/schema versions, producer/provenance, authoritative scope and import metadata.
- KnowledgeUnitRecord — stable ID, version, key/title, authored content, lifecycle status, provenance and content hash.
- KnowledgeComponentRecord — stable ID, version, provisional component kind, semantics, importance/metadata, lifecycle and provenance.
- UnitComponentLink — Unit-to-Component reference/membership without implying exclusive ownership.
- RecallFormRecord — stable ID/version, semantic prompt/interaction/evaluation definition, targets/exposes declarations, hints/support references and provenance.
- CollectionRecord and UnitCollectionLink — organization/navigation only.
- AssetRecord — identity/version or content hash, MIME/type, path/storage reference, provenance and integrity metadata.
- LearningEpisodeRecord — bounded learner interaction episode.
- LearningEventRecord — deterministically ordered typed events within an episode.
- Observation payload — raw learner/system observation attached to the relevant event.
- Historical EvaluationOutcome — evaluator result with evaluator identity/version and provenance.
- Historical MemoryEvidence — interpretation linked to source observation/outcome and mapping provenance.
- LearnerModelStateRecord — rebuildable model-specific state payload with model ID/version and derivation boundary.
- ScheduleStateRecord — rebuildable next-review / urgency / strategy-specific state.
- LearnerConfigRecord — strategy selection, desired-retention or fixed-interval configuration, app defaults/overrides.

## 7. Knowledge identity, version and content integrity
- Every durable Knowledge entity uses an opaque stable ID generated by the Knowledge producer or local legacy adapter.
- Entity identity is separate from optional mutable key/slug/title.
- Same ID + same version must imply semantically identical content. A different normalized content hash at the same version is a conflict.
- Incoming higher version may update the current Knowledge representation after reconciliation rules pass.
- Incoming lower version does not overwrite a newer local version.
- Retired Knowledge remains addressable for historical interpretation.
- Split/merge creates new IDs and optional lineage; learner state is not automatically copied or averaged.

## 8. Knowledge lifecycle and current-version storage
The MVP may keep only the current active Knowledge representation in the main query tables, provided historical learner events contain sufficient execution snapshot/version references for interpretation and full backup preserves any historical assets required by those snapshots.
Knowledge lifecycle:
active
  ↓ content update, same identity
active version N+1
  ↓ no longer offered for new review
retired

Hard delete:
exceptional maintenance operation only
not normal knowledge evolution
- Retiring a Collection never deletes its KnowledgeUnits.
- Removing a Unit from an authoritative scope changes membership/lifecycle according to reconciliation; it does not erase learner history.
- Historical events must remain interpretable even if the referenced current Knowledge entity is retired or later changed.

## 9. LearningEpisode and LearningEvent persistence
LearningEpisode
  id
  schema_version
  knowledge_unit_id
  recall_form_id / version
  episode_type
  started_at / completed_at
  context payload

LearningEvent
  id
  episode_id
  sequence_no
  event_type
  occurred_at
  recorded_at
  payload
  provenance
- sequence_no is deterministic within an episode and is not inferred from wall-clock ordering.
- occurred_at represents when the learner interaction happened; recorded_at represents local persistence/sync time.
- The MVP does not require one globally ordered sequence across independent episodes/devices.
- Normal application behavior appends events; it does not mutate prior learner interactions.
- Corrections, if later supported, are new events or correction records that reference prior history.

## 10. Observation, evaluation and evidence payload contract
Conceptual separation must be retained even if the MVP serializes these together in one event payload.
event_payload:
  observation:
    response_type: self_rating
    response: hard
    response_time_ms: 6200

  historical_evaluation:
    evaluator_id: self_assessment
    evaluator_version: 1
    outcome: hard

  historical_evidence:
    mapper_id: flashcard_self_rating_v1
    mapper_version: 1
    entries:
      - target_component_id: kc_...
        interpretation: weak_positive_or_uncertain

  execution_snapshot:
    recall_form_id: rf_...
    recall_form_version: 3
    prompt_snapshot: ...
- RawObservation fields must not be silently overwritten by later evaluation.
- EvaluationOutcome carries evaluator ID/version and enough structured result for future reinterpretation where practical.
- MemoryEvidence records mapping provenance/version and may be recomputed in future without rewriting the original observation.
- Unknown/ambiguous/insufficient evidence remains explicit rather than defaulting to negative.
- Data minimization applies: preserve the richest observation reasonably needed for reinterpretation without collecting unnecessary sensitive material.

## 11. Append-only history enforcement
The database should make accidental destructive updates to learner history difficult. The exact mechanism is implementation-specific, but the application persistence API must expose append semantics rather than generic update semantics for LearningEvents.
- No Knowledge import transaction may delete or overwrite LearningEpisode/LearningEvent rows.
- No scheduler recalculation may modify historical responses, evaluations, evidence or decision snapshots.
- Backup/restore verifies learner-history counts and integrity metadata.
- Maintenance deletion of learner history, if ever implemented, requires an explicit user-facing destructive operation outside normal review/import code paths.

## 12. Derived learner state contract
Tier A history
  LearningEpisode / LearningEvent
  + Knowledge references/snapshots
        ↓
State Reducer / MemoryModel
        ↓
learner_model_state      # materialized cache
        ↓
SchedulingPolicy
        ↓
schedule_state           # materialized cache
- learner_model_state includes model ID/version and model-specific payload; the core schema does not universalize FSRS stability, BKT P(known), or another algorithm’s internals.
- Derived state must record sufficient derivation provenance/boundary to determine whether it is stale.
- Deleting derived learner state followed by replay must produce an equivalent current state for deterministic models under the same inputs/config.
- Unknown state is represented separately from low/forgotten state.
- MVP analytics such as mastery/urgency are projections, not authoritative learner facts.

## 13. Schedule-state contract
Schedule state is replaceable. The MVP may persist due timestamps/intervals for performance and compatibility, but they remain decisions/materialized state rather than learner-history truth.
- FixedIntervalStrategy may persist legacy interval and next_due_at.
- AdaptiveStrategy may persist strategy-specific cache required for efficient local review.
- Historical scheduling decisions may be captured inside the event/episode decision snapshot for audit, while current schedule_state may later be recalculated.
- Re-inference of learner state and rescheduling are separate operations.
- Changing strategy configuration must not mutate historical events.

## 14. Import transaction and reconciliation persistence
BEGIN TRANSACTION
  validate package + checksums
  stage parsed entities
  match stable IDs
  build ChangeSet
  validate versions/conflicts/scope
  apply Knowledge changes
  apply collection/membership changes
  record import run/change summary
COMMIT

On any validation/apply failure:
ROLLBACK
- No partial Knowledge import is visible after a failed transaction.
- Learner history tables are outside normal import write scope.
- Same-version/different-hash conflict blocks silent overwrite.
- Authoritative absence has meaning only inside the package’s declared authoritative scope.
- Missing entities outside an authoritative scope are unchanged.
- Import records should retain enough metadata to diagnose which package/version produced a Knowledge update.

## 15. Legacy migration
Legacy migration must be conservative: preserve what is known, generate stable local identities, and do not fabricate evidence that the legacy app never captured.
Legacy Collection
  → Collection

Legacy Card
  → KnowledgeUnit
      ├─ KnowledgePoint (minimal target)
      └─ RecallForm (self-assessed front/back)

Legacy review/schedule data
  → learner history or migration snapshot only where facts are recoverable
  → current fixed-interval schedule state where needed for continuity
- Legacy IDs should map deterministically to newly generated stable Mneme IDs and the mapping must be persisted during migration.
- Existing front/back content is preserved without requiring an immediate UI rewrite.
- Existing collection membership is preserved.
- If historical per-review data is unavailable, do not invent LearningEvents. Preserve current scheduling state as migrated state/config and mark provenance as legacy migration.
- If only aggregate review counts/last-review timestamps exist, retain them as migration metadata or derived seed, not fabricated raw observations.
- Migration is versioned and must be idempotent or protected by a migration marker so it cannot duplicate Knowledge/history on repeated startup.

## 16. Schema migration policy
- Database schema version is an implementation version and is distinct from Knowledge schema, event schema, backup format and algorithm versions.
- Migrations are forward-only in normal application upgrades and run transactionally where supported.
- Migration code must preserve stable entity IDs and learner history IDs.
- Additive schema changes leave historical fields absent/unknown rather than synthesizing false values.
- Semantic changes use new fields/payload versions or decoders rather than silently redefining existing stored meaning.
- Maintain migration fixtures representing legacy app data and every shipped Mneme database version that remains supported.

## 17. Backup and restore persistence contract
Full Mneme Backup
├── knowledge/
│   ├── units/components/recall forms
│   └── assets + provenance
├── history/
│   └── learning episodes/events
├── config/
│   └── learner/app scheduling config
├── interpretation/
│   └── historical evaluation/evidence as retained
└── derived/                # optional/rebuildable
    └── learner/schedule state
- Backup is a portable Mneme-native format, not merely a copy of the SQLite file.
- Restore validates backup/schema versions and checksums before writing.
- Fresh-install/replace restore is the MVP priority; merge restore may remain future work.
- After restore, derived learner/schedule state may be rebuilt rather than trusted blindly.
- Any referenced historical asset required to interpret events must remain available or be represented by a durable historical snapshot/reference.

## 18. Concurrency, transactions and crash safety
- Review completion writes the episode/events and any immediate derived-state update in a crash-safe transaction or in an order that allows derived state to be rebuilt after interruption.
- If event append succeeds but cache update fails, history wins; cache is repaired/rebuilt.
- Knowledge import never runs as an unsafe sequence of independent row updates visible mid-import.
- Asset file writes use staging/rename or equivalent integrity checks so database references do not point to half-written files.
- The MVP assumes one local active writer unless Flutter/platform implementation requires otherwise; future sync must not be simulated with unsafe last-write-wins over learner history.

## 20. Data privacy and retention
- Offline-first local persistence is the default; no learner history requires a backend for core operation.
- Raw responses are retained only where their future reinterpretation value justifies the data collected.
- Large or potentially sensitive artifacts may use configurable retention in future versions; the MVP must at least avoid collecting unnecessary data by default.
- Logs/debug exports must not unintentionally include full raw responses or private Knowledge content unless explicitly requested.
- AI/Matrix integrations remain optional and must not silently copy local learner history into remote services as part of normal persistence.

## 21. MVP implementation sequence
- Inventory the existing Flutter persistence model, legacy Card/Collection fields, review-history availability and scheduling data.
- Introduce stable Mneme IDs and database migration marker/versioning.
- Create KnowledgeUnit/KnowledgeComponent/RecallForm/Collection/Asset persistence and repositories.
- Implement package import staging, validation, reconciliation and transaction boundaries.
- Introduce LearningEpisode/LearningEvent append-only persistence and migrate the current self-assessed flashcard review path.
- Persist RawObservation, minimal historical EvaluationOutcome/MemoryEvidence and execution snapshot.
- Add rebuildable learner-model state and fixed/adaptive schedule-state repositories.
- Implement legacy Card migration and verify UI behavior remains equivalent.
- Implement portable full backup/restore and rebuild verification.
- Add migration, reconciliation, replay, crash-safety and restore test fixtures.

## 22. Acceptance criteria
- Existing legacy flashcards and collections migrate without loss of visible content or collection organization.
- Every migrated/new KnowledgeUnit, KnowledgeComponent and RecallForm has a stable durable ID and version.
- Knowledge import is transactional and cannot silently overwrite same-ID/same-version conflicting content.
- Knowledge import/update cannot delete or mutate learner LearningEpisode/LearningEvent history.
- Each completed MVP flashcard interaction can be represented as an ordered LearningEpisode with at least one LearningEvent.
- RawObservation, historical evaluation and historical memory evidence remain semantically distinct even if serialized together.
- Learner-model and schedule state can be deleted and rebuilt without loss of authoritative learner history.
- Unknown learner state is not stored or displayed as zero/forgotten merely because evidence is absent.
- Derived state records the model/strategy provenance necessary to detect stale caches.
- Failed package import leaves the prior Knowledge database unchanged.
- A crash after history append but before derived cache update can recover by rebuilding cache.
- Portable backup/restore can recover Knowledge, learner history and config on a clean install.
- Database migration does not fabricate historical learner evidence unavailable in the legacy app.
- Future Structure/Procedure and richer event payloads can be added without redefining existing stored semantics.

## 23. Non-goals for Requirement 04
- Defining a universal normalized SQL schema for all future Mneme component/event types.
- Implementing cloud sync, CRDTs, multi-device conflict resolution or collaborative editing.
- Implementing learned EvidenceMappers, research ModelRun infrastructure or cross-domain learner models.
- Persisting one canonical mastery scalar for every KnowledgeComponent.
- Replacing the current Flashcard UI with multi-step tutoring experiences.
- Using raw SQLite as the portable backup/interchange protocol.

## 24. Persistence invariants
- Durable history beats derived cache.
- Knowledge import never owns learner history.
- Stable identity is independent of title/path/collection membership.
- Version conflicts fail visibly; they are never silently merged by hash mismatch at the same version.
- Retired is not deleted.
- Unknown is not weak.
- Observation is not evidence; evidence is not learner-state truth.
- Model state and schedule state are replaceable.
- Conceptual separation does not require one-table-per-concept.
- Legacy migration preserves known facts and does not invent unknown history.
- Portable backup is lossless for durable Mneme data and independent of local database layout.

## 25. Handoff to implementation
Once this requirement is accepted, the engineering work can move from requirements to a concrete Flutter persistence design. The next artifact should be an implementation specification containing the selected SQLite schema, migration SQL/steps, repository interfaces, serialization types, transaction boundaries, and test plan. That implementation specification may optimize aggressively, provided it remains conformant with the persistence invariants above.

## 26. Implementation architecture amendments (v1.1)
Requirement 04 v1.1 incorporates implementation guardrails derived from source-code review of DeepSeek Harness/Cordis, Hermes Agent memory providers, and Pi. These patterns refine persistence/runtime boundaries without changing the Mneme Foundation ontology.
- Canonical learner history is distinct from all derived projections, summaries, checkpoints and caches.
- Runtime coordination events are a separate event domain from durable LearningEvents.
- Persisted artifacts do not automatically participate in learner inference; consumers must be explicit.
- Unknown semantically required historical event types fail safely; only explicitly ignorable events may be skipped.
- System-provided hints, answer reveals, worked examples and related RecallForms retain exposure provenance for later evidence interpretation.
- Replaceable capabilities follow Definition → Provider → Consumer seams but do not require a dynamic plugin framework.
- Long histories may use replay checkpoints as optional accelerators; checkpoints never replace canonical history.
- Purpose-specific projections are preferred over one universal learner-summary record.
- Semantic event order is explicit and does not depend solely on wall-clock or asynchronous completion order.
- Optional AI/remote processing may be asynchronous and fail open; canonical local history persistence must not be best-effort.

## 30. Additional v1.1 persistence invariants
- Lossy projections never replace canonical history.
- Durable does not imply active in inference.
- Unknown required historical semantics fail safely.
- System exposure provenance survives into later evidence interpretation.
- Replay checkpoints accelerate reconstruction but are never authoritative.
- Optional services fail open; canonical local learner-history writes fail closed and visibly if durability cannot be guaranteed.

## 31. Pi 1.0 + claude-mem Persistence Amendments (v1.2)
This section supersedes or sharpens v1.1 implementation guidance where Pi 1.0 and claude-mem provide additional engineering evidence.

### 31. Canonical HistoryProjector / normalizer
Introduce one shared historical normalization/projection boundary between persisted event envelopes and downstream consumers. MemoryModel rebuild, scheduler, diagnostics, backup/research export, and audit tooling must reuse this semantics rather than each interpreting event payloads independently. Unknown required event semantics fail safely.

### 32. Durable operation identity and idempotency
A learner review/episode commit carries an operation_id (or equivalent durable submission identity). The transaction enforces at-most-one committed historical mutation per operation identity. Crash/retry after a successful commit returns/reuses the existing result rather than creating duplicate evidence.

### 33. ReplayCheckpoint v1.2 contract
ReplayCheckpoint becomes a first-class rebuild accelerator. It records: checkpoint ID; history-through boundary; MemoryModel definition/version; fitted parameter identity/version; model-state snapshot; Knowledge/event/evidence schema boundaries; relevant Knowledge artifact versions or snapshot/hash set; evaluator/evidence-mapper interpretation boundary when required; creation provenance/checksum. A checkpoint is never authoritative and is ignored when dependencies are incompatible.

### 34. Bounded and incremental history APIs
Repository interfaces must not assume full learner history fits in memory. Support pagination/ranges, since-boundary reads, by episode, by Knowledge target/component, and compatible-checkpoint + incremental-event rebuild. Full replay remains a correctness fallback, not the normal runtime path for long-lived datasets.

### 35. Interpretation overlay / supersession
Raw observations are immutable. Re-evaluation/re-attribution appends new EvaluationOutcome/MemoryEvidence interpretations with derived_from/supersedes/reinterprets provenance. A current preferred interpretation is a projection, not an in-place rewrite of history.

### 36. Artifact-specific consolidation policy
Knowledge/derived artifacts may run exact duplicate checks or produce fuzzy duplicate candidates. Canonical learner events/observations never use semantic deduplication. Historical deduplication is limited to operation-id idempotency. Semantic similarity cannot establish Knowledge identity.

### 37. Retrieval indexes and progressive read models
Exact ID/structured queries remain authoritative. FTS and semantic indexes are rebuildable read models used for discovery. History and rich Knowledge should support Index → Context → Detail reads so consumers fetch full payloads only when required.

### 38. Purpose-specific ProjectionBudget
Derived projections may declare a budget (time, bytes/chars/tokens, result count plus measured cost) and a degradation policy. Projection should drop whole low-value layers/items rather than corrupting semantic records by arbitrary truncation. Budgeting belongs to read/selection projections, not canonical storage.

### 39. Local-first sync and enrichment
Local SQLite/canonical repositories serve current review, scheduling, Knowledge lookup and durable commits. Remote sync, embeddings, cloud services and AI processing may be nudged asynchronously and can improve future state, but must not block local use. Network failure leaves current local review functional.

### 40. v1.2 persistence acceptance additions
- Retrying the same operation_id produces one historical interaction.
- A changed EvidenceMapper can append a reinterpretation without mutating RawObservation.
- A stale/incompatible ReplayCheckpoint is safely ignored and replay continues from an earlier boundary/full history.
- Scheduler/diagnostics/rebuild share the same HistoryProjector event compatibility semantics.
- Semantic indexes can be deleted/rebuilt without loss of Knowledge or learner history.
- A test dataset larger than comfortable in-memory history can rebuild incrementally.
- Local review remains usable when remote sync/AI/vector services are unavailable.

## 41. Dual-Profile Persistence Boundary (v1.3)

### 41.1 Shared-core persistence primitives
- Stable IDs/version/provenance/lineage and integrity metadata may share physical persistence libraries or schemas only when profile/type identity remains explicit.
- MemoryScope and HistoryBoundary are shared concepts; profile-specific scope facets and event payloads remain namespaced.
- ReplayCheckpoint is always tied to a declared profile/model/projection family and cannot be applied across profiles merely because storage formats match.
- FTS/vector/semantic indexes remain derived and rebuildable for both profiles; index deletion cannot delete canonical learning history or canonical agent source observations.
- Portable backup must record profile/type/schema identity so a restore never interprets Agent Memory records as LearningEvents or vice versa.

### 41.2 Agent Memory storage is not Minion-Agent SessionStorage
Minion-Agent owns authoritative conversation/session execution history, including its own durability/replay requirements. Minion-Memory owns long-term memory observations/records/indexes/projections. An adapter may persist stable references between them, but neither store is a replacement for the other.

### 41.3 Agent Memory durability rule
When the Minion-Agent adapter observes an authoritative session/turn record, it must durably capture enough source reference/provenance before optional extraction, consolidation, embeddings, remote sync, or AI enrichment. Agent-memory derived work may be asynchronous and retryable; loss of optional derived state must not corrupt Minion-Agent session history.

## 42. v1.3 Acceptance Additions
- Restoring a mixed-profile backup preserves profile/type identity and never cross-decodes records.
- Deleting/rebuilding agent-memory search indexes leaves canonical source observations and MemoryRecords intact.
- A Minion-Agent memory projection can be traced to record IDs/versions and its source/projection policy without copying the entire session log into Minion-Memory.
- Conversation compaction and memory consolidation are independently testable and cannot rewrite each other's canonical records.
- Scope isolation tests prove that a memory outside the allowed principal/agent/project/conversation scope cannot be returned merely because semantic similarity is high.
