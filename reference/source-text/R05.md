PROJECT MNEME
Requirement 05 — Agent Memory Profile & Minion-Agent Integration v1.0
Primary Agent-Memory Use Case
Aligned with Foundation v2.3, MVP Contract v1.2, Requirement 04 v1.3, and Implementation Architecture Amendments v1.3

## 1. Purpose
Define the first Agent Memory Profile for Minion-Memory and its integration contract with Minion-Agent. The profile covers durable long-term memory capture, scope, derivation/consolidation, retrieval, context projection, provenance, feedback-loop prevention, and adapter boundaries. It deliberately does not reuse human-learning entities where their semantics do not fit.

## 2. Normative Dependencies and Authority
- Project Mneme Foundation v2.3 is the architectural authority.
- MVP Contract v1.2 defines the shared-core/profile split.
- Requirement 04 v1.3 defines shared persistence compatibility rules; it does not make agent memory a LearningEvent store.
- Implementation Architecture Amendments v1.3 supplies implementation guardrails.
- Minion-Agent source/design is an integration target and evidence source, not Mneme semantic authority.

## 4. Boundary: Session History vs Long-Term Memory
Minion-Agent Session / Conversation History
  authoritative execution record
  messages / tool results / request state / compaction / forks
        |
        | stable source references
        v
Minion-Memory Agent Memory Profile
  capture observations
  derive/consolidate MemoryRecords
  build indexes
  retrieve under scope + budget
  project context for a future request
The two stores may reference each other but do not replace each other. Clearing/compacting a conversation is not equivalent to deleting/consolidating long-term memory. Rebuilding memory indexes cannot alter agent execution history.

## 5. Agent Memory Domain Model

### 5.1 AgentMemoryObservation
A durable source observation about agent-relevant information. It records what source material was observed and enough provenance to reason about origin without claiming the extracted content is already a trusted memory fact.

| Field family | Semantics |
|---|---|
| id / version | Stable opaque identity and schema/semantic version as applicable |
| source_ref | Stable reference to Minion-Agent session/turn/message/tool/artifact when available |
| occurred_at / recorded_at | Source-time versus local durable-capture time |
| scope | MemoryScope facets applicable to this observation |
| origin | external/user/tool/environment vs recalled/injected/system-generated context |
| payload/content_ref | Privacy-bounded raw/structured observation or content-addressed reference |
| provenance | producer, adapter version, capture policy/version |


### 5.2 MemoryRecord
A derived durable long-term-memory artifact. It may represent a fact, preference, decision, project convention, procedure, relationship, event summary, or another profile-defined kind. The taxonomy is provisional. Every MemoryRecord retains source lineage and may be superseded, merged, split, or retired without rewriting source observations.

### 5.3 MemoryScope
Scope is a correctness/privacy boundary, not a ranking hint. The MVP must support an extensible structured scope sufficient to express principal/user, agent identity, workspace/project, conversation, session, and task applicability. Retrieval must enforce scope before semantic ranking can admit a candidate.

### 5.4 ConsolidationOutcome
Consolidation is a derived interpretation over observations/records. It may create, update-by-new-version, supersede, merge, split, or retire MemoryRecords. It never deletes or semantically merges AgentMemoryObservation history. Every consolidation result records policy/producer/version and source lineage.

### 5.5 RetrievalQuery and RetrievalCandidate
RetrievalQuery carries purpose, allowed scope, structured filters, query text/embedding input where used, and a projection budget. Candidate retrieval may combine exact identity, structured query, lexical search, semantic similarity, recency/importance/utility signals, and profile-specific ranking. Similarity is discovery, never identity or authority.

### 5.6 AgentContextProjection
A lossy, purpose-specific representation of selected MemoryRecords for one agent request. It records projection policy/version, selected record IDs/versions, scope, budget/cost, and a stable projection identity/content reference when needed for request reconstruction.

## 6. Capture Pipeline
authoritative Minion-Agent turn/session commit
        ↓
Agent adapter capture
        ↓  durable source reference + origin/scope
AgentMemoryObservation
        ↓
optional async extraction / enrichment
        ↓
ConsolidationOutcome -> MemoryRecord(s) -> derived indexes
- Capture of source references/provenance is the durability barrier. Expensive extraction, embeddings, LLM summarization, or cloud sync may happen later.
- Capture must be idempotent by durable operation/source identity so crash/retry cannot create duplicate source observations.
- The adapter must not block the agent request/turn critical path on optional enrichment.
- Privacy/retention policy may intentionally avoid retaining full raw content; the retained representation must still be honest about what was not preserved.

## 7. Context Fencing / Anti-Feedback Contract
Any memory context injected into Minion-Agent must be attributable to specific MemoryRecord/projection identities. Subsequent capture must know which information was system-provided so an assistant repetition is not treated as independent new memory.
MemoryRecord R7
  ↓ retrieve
AgentContextProjection P12 [contains R7]
  ↓ inject into request/header["memory"]
assistant repeats R7
  ↓ capture
origin includes recalled_projection=P12 / record=R7
  ↓
NO independent reinforcement unless new external evidence corroborates it

## 8. Retrieval and Progressive Disclosure
- Authority order: stable identity / explicit record reference first; structured scope/filter next; lexical/semantic search for discovery.
- Read architecture SHOULD support Index → Context → Detail so broad searches do not require hydrating full memory payloads.
- Ranking MAY use recency, reinforcement/confirmation, utility, source quality, importance, or domain signals, but no particular universal score is frozen.
- Hard scope/privacy constraints apply before ranking and cannot be overridden by similarity.

## 9. Projection Budget
Agent-context retrieval is budgeted by actual resource cost where feasible (characters/tokens/records/latency), not merely a fixed count. Degradation/removal applies only to the projection; canonical observations and MemoryRecords are unchanged.

## 10. Minion-Agent Adapter Contract

| Stage | Adapter responsibility |
|---|---|
| Pre-request | Build RetrievalQuery from agent/user/workspace/conversation/task context; retrieve and project memory within budget. |
| Request assembly | Provide exact memory projection through a Minion-Agent prompt/header seam; preserve projection identity and record-version references. |
| Post-turn capture | After authoritative session history exists, capture source references and origin context idempotently. |
| Async enrichment | Run extraction/consolidation/indexing without blocking critical agent operation. |
| Failure | Fail open for optional memory recall/enrichment; never corrupt or rewrite Minion-Agent session history. |

The adapter MAY be packaged as a Minion-Agent plugin/service provider because Minion-Agent already uses that runtime architecture. The Minion-Memory engine itself MUST NOT require Minion-Agent/Cordis plugin infrastructure.

## 11. Request Reconstruction and Audit
When memory context is model-visible, the integration must preserve enough information to explain/reconstruct the memory projection that was dispatched: projection identity or content reference, selected MemoryRecord IDs/versions, policy/version, scope, and relevant budget. This complements Minion-Agent’s content-addressed request-header invariant.

## 12. Persistence and Indexing
- Canonical: AgentMemoryObservation and committed MemoryRecord lineage/consolidation history according to retention policy.
- Rebuildable: lexical/vector indexes, ranking caches, summaries, embeddings when their source/policy is retained, and AgentContextProjection caches unless audit policy makes the exact projection durable.
- ReplayCheckpoint may accelerate rebuild of a derived projection/index family but never substitutes for source observations/records.
- SQLite is a recommended local runtime backend; portable exports may use JSONL/structured manifests. Backend choice is not semantic authority.

## 13. Relationship to Learning Profile

| Learning Profile | Agent Memory Profile |
|---|---|
| LearningEpisode / LearningEvent | AgentMemoryObservation / source capture |
| EvaluationOutcome / MemoryEvidence | Consolidation/record derivation (different meaning) |
| LearnerMemoryModel | Retrieval/ranking/consolidation policy |
| SchedulingPolicy / RecallForm selector | AgentContextProjection selection |
| Exposure provenance | Context fencing / recalled-memory provenance |

These correspondences are architectural analogies only. They are not type aliases and do not authorize one profile to interpret the other’s data.

## 14. Failure and Recovery
- Retrying the same capture operation/source identity is idempotent.
- Failure after source capture but before extraction leaves a recoverable pending enrichment state; it does not lose the source reference.
- Index loss/rebuild does not change MemoryRecord identity or lineage.
- Unknown required record/event schema fails safely rather than silently omitting semantics.
- Minion-Agent remains functional if Minion-Memory is unavailable; memory degradation is observable but not fatal unless the application explicitly configures memory as mandatory.

## 15. Privacy and Retention
Agent memory may contain user, project, tool, workplace, or other sensitive context. Scope enforcement, retention, deletion/retirement semantics, raw-content minimization, and auditability are therefore first-class. Telemetry must prefer bounded metadata over content. A projection may omit private records even when semantically relevant.

## 16. MVP Acceptance Criteria
- The same canonical Agent Memory conformance scenarios pass in Python and Rust without one implementation acting as oracle for the other.
- A Minion-Agent adapter can inject a scoped/budgeted memory projection through the existing request/prompt seam and identify the exact records used.
- A repeated assistant statement originating solely from injected memory does not create independent reinforcement.
- Two source observations with similar text remain distinct; consolidation may relate them without deleting lineage.
- Scope isolation blocks an out-of-scope semantically similar memory.
- Exact/structured lookup continues to work with semantic indexing disabled.
- Optional extraction/vector/AI failure does not block authoritative session commit or durable source capture.
- Deleting indexes/checkpoints and rebuilding produces equivalent discoverability/projections for deterministic policies.
- Minion-Agent SessionStorage and Minion-Memory storage can fail/recover independently without corrupting the other.

## 17. Deferred / Provisional
- Exact MemoryRecord taxonomy.
- Universal importance/trust/reinforcement score.
- Learned consolidation/ranking model.
- Cross-agent automatic memory sharing policy.
- Specific embedding model/vector database.
- Automatic promotion of agent memory into authored Knowledge.
- Global personal profile synthesis.

## 18. Final Invariants
- Session history != long-term memory.
- Capture != consolidation != retrieval != projection.
- Persisted != automatically active.
- Similarity != identity.
- Scope is enforced before ranking.
- Recalled context is never silently re-learned as independent new memory.
- Agent policy != learner scheduling policy.
- The adapter may use Minion-Agent runtime seams; the memory engine remains independently usable.
