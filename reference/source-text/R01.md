Flashcard App – Requirement 01
Knowledge Package, Import, Reconciliation & Local Knowledge Storage
Mneme Foundation v2.3 / MVP Contract v1.2 aligned — Learning Profile

## 1. Purpose
Define the Learning Profile portable Knowledge Package, parsing/validation, stable-identity reconciliation, local Knowledge storage semantics, collection hierarchy, assets, provenance, and legacy Markdown adapter. Learner history is never owned by import. Agent Memory records are not Knowledge Package entities unless a future explicit adapter maps them into authored Knowledge.

## 2. Normative dependencies
Requirement 00 is the domain authority. Requirement 04 owns concrete persistence layout. This requirement owns interchange and reconciliation semantics.

## 3. Canonical package shape
MVP canonical interchange remains manifest.yaml + units/*.md + assets/*. One KnowledgeUnit per Markdown entity file. Entity files own KnowledgeUnit semantics; manifest owns package semantics, scope, producer/provenance, entry integrity, schema version, authoritative flag, and package-level shared definitions such as Collections.

## 4. Knowledge identity and versions
Every durable KnowledgeUnit, KnowledgeComponent, RecallForm, Collection, Asset and versioned support artifact has an opaque stable ID. Same ID + same version must imply same semantic content/hash. Higher incoming version may update; same version + different content is a conflict; older incoming versions do not silently overwrite newer local versions.

## 5. Unit-local serialization is not identity ownership
For MVP convenience, components may be serialized inside a unit file. This does not mean the unit owns the conceptual identity of every component forever. Schema/IDs must permit future cross-unit reuse without requiring MVP canonicalization or global ontology.

## 6. RecallForm package semantics
RecallForm declares stimulus/prompt semantics, response/interaction specification, evaluator reference or deterministic evaluation definition, target KnowledgeComponents, exposed KnowledgeComponents/information, support/hints, and versioned EvidenceMapping when declarative. Renderer UI remains outside the package semantics.

## 7. Collections and navigation
Collections are lightweight organization/navigation metadata, many-to-many with KnowledgeUnits, with stable IDs and optional single-parent hierarchy for MVP. Smart learner views such as Due/Weak are not Knowledge Collections.

## 8. Assets
Assets use package-relative references and integrity hashes. Canonical packages do not depend on remote URLs or base64 blobs. Large media may be externalized inside the package asset tree.

## 9. Validation pipeline
Package → structural validation → semantic validation → parse domain model → compute ChangeSet → transactional reconciliation. Reject invalid IDs/versions, path traversal, checksum failures, malformed semantic references, and unsupported required schema features before mutating local state.

## 10. Reconciliation
Match strictly by stable ID. States: Added, Updated, Unchanged, Missing, Conflict, Retired. Non-authoritative absence has no meaning. Authoritative absence has meaning only inside declared scope and normally removes membership/candidate-retires rather than hard-deleting an entity with history.

## 11. Split, merge and lineage
Split/merge creates new stable IDs and optional lineage metadata. Learner state is not automatically copied or averaged into new entities. Historical references remain interpretable through preserved versions/snapshots.

## 12. Provenance
Knowledge artifacts must be able to carry producer, source material/reference, generation method (human/AI/import), created/updated time, source package, and lineage/correction metadata. Provenance is not learner evidence.

## 13. Duplicate detection is advisory unless identity is certain
Stable ID is authoritative. Controlled exact semantic keys may support deterministic checks inside a namespace, but lexical/semantic similarity can only produce duplicate candidates/warnings. Similarity must never silently merge distinct Knowledge identities. Rare discriminating differences must be treated as a reason to avoid automatic merge.

## 14. Retrieval/read model
Knowledge access should support exact ID/key lookup and structured queries first. FTS/lexical and semantic retrieval are optional discovery layers. A semantic index is rebuildable and never authoritative. Rich KnowledgeUnits should support progressive disclosure: Index/Summary → relevant component/context → full detail/support.

## 15. Local-first behavior
Import, Knowledge browse, and review must use the local canonical store. Remote sync or semantic-index services may refresh asynchronously and must not block current local reads.

## 16. Legacy Markdown adapter
Existing Markdown collections/cards remain importable through an adapter that produces KnowledgeUnits, KnowledgePoints, RecallForms and collection membership with generated stable IDs/provenance. Re-import must preserve stable IDs when the adapter can deterministically recover them.

## 17. Transaction and history isolation
Knowledge reconciliation occurs transactionally and must never delete/rewrite LearningEpisode/LearningEvent/RawObservation history. Knowledge retirement only changes current Knowledge lifecycle/membership.

## 18. Compatibility
Package schema version is separate from database schema, event schema, backup format, model version, and evaluator/evidence-mapper versions. Unknown required Knowledge semantics must fail safely; explicitly ignorable metadata may be skipped.

## 19. Acceptance criteria
A package can be validated without mutation; identical re-import is idempotent; same-ID/same-version content drift conflicts; authoritative scope does not delete unrelated entities; semantic duplicate candidates never auto-merge; learner history remains unchanged after any Knowledge import/update; local review works without network or embedding service.

## 20. Handoff to Requirement 04
Requirement 04 maps these durable semantics to repositories, transactions, indexes, migrations, checkpoints, backup and SQLite implementation choices.

## 21. Dual-Profile / Agent-Memory Boundary (v2.3)
- Knowledge Package remains an authored-learning interchange protocol, not a generic agent-memory import format.
- Agent Memory capture/consolidation must not silently mint KnowledgeUnit identity from semantically similar MemoryRecords.
- A future Knowledge Builder may promote validated agent-derived material into Knowledge through an explicit provenance-preserving transformation; this is not implicit consolidation.
- Shared retrieval infrastructure may index Knowledge and Agent Memory, but namespaces/scopes and stable identities remain distinct.
